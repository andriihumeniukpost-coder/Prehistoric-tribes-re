3. Slot-map write/clear evidence
--------------------------------
In analysis/bytecode/c.txt, private void h(int), bytecode 0–18 writes k[2] to g.e[4444 + this.v].
In private void c(byte), bytecode 92–98 writes zero to g.e[4444 + argument_1]. This happens on the successful replacement path before the later copying loop. It does not itself establish that the old slot marker was cleared; the separate marker write at 346–356 remains the cleanup proof.
In private void am(), bytecode 177–186 writes -1 to g.e[4444 + this.v] on its guarded path.
In private void an(), bytecode 292–301 writes zero to g.e[4444 + this.v] on one branch.
These differing writes show that the mapping region has its own lifecycle and should not be treated as an immutable entity-to-slot map. Their exact semantics depend on call paths and the surrounding table values.

5. Interpretation for the slot-reuse question
----------------------------------------------
- State bytes at 2828+index and slot markers at 1919+slot are separate regions.
- The slot-map region at 4444+index is actively changed by multiple methods, including zero and -1 writes. Therefore a failed replacement cannot be analyzed by assuming the mapping is necessarily preserved forever.
- The known successful replacement path resets the old marker to zero at c.c(byte) bytecode 346–356. A full group returns at bytecode 429 before that point.
- Static bytecode still does not prove whether a given failed entity is scheduled for another attempt, whether its mapping is later cleared/rewritten in a way that loses its source slot, or whether another code path frees the old marker.
