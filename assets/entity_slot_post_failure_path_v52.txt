Prehistoric Tribes v0.1.38 — post-failure state/mapping audit (v52)
====================================================================

Input: Prehistoric-tribes-analysis-bundle-20261012-v51.zip. Static analysis of the supplied disassembly only. Original game code was not modified.

Question
--------
After c.k() encounters state 107 and calls c.c(byte), can the tail of c.i() or c.I() directly clear the source slot marker / mapping or alter the state so the same entity is not retried?

1. c.i() dispatch tail
----------------------
Class c, private boolean i(), bytecode offsets 1014–1030:
- 1014: invokespecial k:()Z
- 1018: ifeq 1023
- 1021–1022: return true when k() returns true.
- 1023–1026: invoke I:()V only when k() returns false.
- 1027–1028: return true after I() completes.
- 1029–1030: return false is the earlier branch for a different condition, not the post-k tail.

This means I() is NOT executed after every state-107 replacement attempt: if k() returns true, i() returns immediately. If k() returns false, I() executes. The bytecode proves this control-flow split; it does not by itself establish which return is taken for every failed replacement.

2. c.k() around state 107
-------------------------
Class c, private boolean k(), offsets 326–361:
- 326–341 read g.e[2828 + v] and compare with 107.
- 344–358 load g.e[4444 + v] and invoke c(byte).
- Execution then continues at offset 361 with further state checks; the call does not return a success flag.

The full-group path in c.c(byte) returns at offset 429 before the successful-path writes at offsets 88–98 (mapping cleanup) and 346–356 (source marker reset). This remains direct evidence that those two cleanups are skipped on that path.

3. What c.I() can and cannot do directly
----------------------------------------
Class c, private void I(), bytecode offsets 0–498:
- The method reads state g.e[2828 + v] and performs various scene/entity updates.
- It contains calls to private a(int, byte) at offsets 137–157 and 345, which can change the state region indirectly.
- It contains no direct reference to literal offset 1919 or 4444 in its own method body. Therefore, no direct marker-region or mapping-region write is present in c.I() itself.
- A state transition can still occur through a(int, byte), and subsequent state dispatch can therefore differ. This is a meaningful indirect path, not a direct marker reset.

4. State setter a(int, byte)
----------------------------
Class c, private void a(int, byte), offsets 0–114:
- 0–12 compares current g.e[2828 + index] with the new byte.
- If different, offsets 18–35 write zero to g.e[404 + index] and write the new state to g.e[2828 + index].
- The method does not directly write the slot-marker region 1919+slot or mapping region 4444+index in the displayed body.
- It calls C() for certain new state values (offsets 98–111), so a complete transitive side-effect proof would require inspecting C() and its callees. Do not infer a global absence of indirect marker writes from this one method.

5. Defensible conclusion
------------------------
Confirmed:
- Full-group failure in c.c(byte) skips its successful replacement cleanup.
- c.k() continues after c.c(byte) returns.
- c.i() returns immediately if k() is true; otherwise it invokes c.I().
- c.I() can indirectly change state through a(int, byte), but does not itself directly write marker or mapping offsets.

Not confirmed:
- Whether k() returns true or false on every full-group failure.
- Whether the later state handlers preserve state 107 and the same mapping on all paths.
- Whether all transitive callees reachable after the failed replacement are free of marker/mapping writes.
- A permanent/global slot leak.

Next decisive step

Inspect c.C() and the transitive callees reached from a(int, byte), then correlate their effects with the return paths of k() after a failed c.c(byte). Also enumerate computed-index writes into 1919+slot across all methods, not just literal-offset matches.
