Prehistoric Tribes v0.1.38 — entity slot marker write audit v37

Scope
-----
Inspected the javap-style disassembly of g.class in analysis/bytecode/g.txt from bundle v36. Focus: writes to the byte[] field g.e at index 1919 + slot.

Findings supported by disassembly
---------------------------------
1. Allocation method `final byte a(byte, byte, byte, byte, byte)` computes slot index in local 6. At bytecode offsets 972–1002 it uses `e[1919 + slot]` as an input and writes a computed byte back to that same index. The expression is the existing marker + 5 + result of `a(255,10)`, converted to byte. This is the allocation-side marker write.
2. Release method `final void a(byte)` writes -1 to `e[1919 + slot]` at offsets 230–240, after calls `e(slot)` and `f(slot)` and before `c(slot)`.
3. The inspected `final void b(int,int)` loops slots 1..50 and processes a slot only when `e[1919 + slot] > 0`; it does not write the marker in the shown loop.
4. The inspected `private boolean d(int)` contains a loop over indices 1..100 that tests `e[1919 + i] != 0`, but the zero write at offsets 1151–1162 targets `e[808 + i]`, not `e[1919 + i]`. This is a distinct parallel field region and is not a marker reset.
5. Searches of the disassembly for `sipush 1919` locate the above marker allocation and release writes; the other occurrences inspected are reads/conditions. This is evidence about explicit constant-index writes in this disassembly, not a proof against every possible indirect index calculation.

Conclusion
----------
The direct writes observed to the marker region are allocation-side computed marker and release-side -1. No explicit direct write of 0 to `e[1919 + slot]` was found in the audited sites. That makes slot reuse suspicious, but does NOT yet prove a leak: the array may be reinitialized, indices may be reached through a different expression, or another lifecycle path may replace/reset the relevant state. Next decisive step is a complete array-index dataflow audit for every `bastore` whose array reference is g.e, plus constructor/reset call-graph analysis.

Evidence locations
------------------
- analysis/bytecode/g.txt, method `final byte a(byte, byte, byte, byte, byte)`, offsets 972–1002 (allocation marker expression).
- analysis/bytecode/g.txt, method `final void a(byte)`, offsets 230–240 (release marker = -1).
- analysis/bytecode/g.txt, method `final void b(int,int)`, offsets 8–53 and 61 onward (marker-positive gating).
- analysis/bytecode/g.txt, method `private boolean d(int)`, offsets 1137–1162 (marker read followed by write to e[808 + i], not marker region).

Caution
-------
Do not label this a confirmed leak until index dataflow and reset/reinitialization paths are exhausted.
