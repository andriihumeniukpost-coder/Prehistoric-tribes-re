Prehistoric Tribes v0.1.38 — slot-marker lifecycle follow-up (v40)

Scope
-----
Continued from the validated v39 bundle. This pass targeted the exact allocator marker store, the random helper it calls, direct references to the marker band, and every call site found for f.i() in the supplied bytecode disassemblies.

Confirmed bytecode facts
------------------------
1. Allocator g.a(BBBBB)B:
   - bytecode 12–26: reads e[1919 + groupBase + scan] and continues while the byte is nonzero; a zero byte is the free-slot condition.
   - bytecode 982–1004: the marker write uses the prior e[1919 + slot] value, adds 5, adds a(255, 10), converts to byte, and stores it at e[1919 + slot]. This is the slot's allocation marker write.
   - helper g.a(II)I at bytecode 0–11 returns (Random.nextInt() & firstArgument) % secondArgument. Therefore a(255,10) is in [0,9], so when the allocator has accepted a marker of 0, the newly written marker is 5..14. It cannot wrap to 0 or -1 on this allocation path.
2. Release g.a(B)V:
   - bytecode 226–240 calls e(slot), calls f(slot), then stores -1 to e[1919 + slot]; c(slot) is called immediately afterward at 241–243.
   - Thus the explicit release store is -1, not 0.
3. Cleanup-like loop in g (method containing bytecode 1127–1462):
   - bytecode 1137–1148 reads e[1919 + i] for i=1..100 and branches when the marker is 0.
   - bytecode 1151–1162 writes 0 to e[808 + i], not to e[1919 + i]. This does not clear slot markers.
4. f.i()V:
   - f bytecode 6–17 allocates a new byte[9983] and assigns it to g.e. Java initializes this array to all zeroes.
   - The only direct invocation of f.i() found in the supplied disassemblies is f.<init>, at bytecode 313–316. The evidence supports this as initialization during construction of f, not a demonstrated scene-transition reset. The search is limited to the supplied disassembled classes.
5. g.i()V at bytecode 0–63 resets boolean and scalar state fields but does not assign to g.e and contains no array store.

Interpretation
--------------
The observed allocator/release pair is asymmetric: allocation requires marker == 0; release writes -1; allocation writes a positive marker in [5,14]. No marker-band zero store was confirmed in the inspected direct bytecode references. The reset at e[808+i] is a distinct field region.

This is strong evidence for a potential reuse defect in the observed path: after release, the slot's marker becomes -1, which does not satisfy the allocator's marker == 0 check. However, the report does NOT claim a fully proven global leak, because a complete whole-program alias/index proof is not available from the partial stack tracer, and unexamined indirect writes or object reconstruction could still change the outcome. f.i() resets the whole array only when a new f initialization path executes; this pass did not establish any runtime lifecycle that reconstructs f after a slot release.
