ENTITY SLOT REUSE AUDIT v31
===========================

Scope: static bytecode inspection of g.class disassembly in analysis/bytecode/g.txt. This is not a runtime trace.

Confirmed control flow
----------------------
1) final byte a(byte, byte, byte, byte, byte) searches within a 50-slot group at e[1919 + base + candidate]. It advances while the marker is nonzero, and returns -1 when candidate reaches 50 (bytecode text lines 32206-32223). Therefore both positive markers and -1 are unavailable to this allocator.

2) final void a(byte) performs per-slot cleanup calls e(slot), f(slot), then stores -1 into e[1919 + slot], then calls c(slot) (lines 33325-33340). The -1 write is explicit and occurs before c(slot).

3) private boolean d(int) contains a loop over indices 1..100. It tests e[1919 + index] != 0, but the immediate store at e[808 + index] = 0, not e[1919 + index] = 0 (lines 39572-39589). This code does NOT normalize the slot marker to zero. Do not mistake the neighboring zero store for marker reset.

4) Other observed reads treat marker according to different predicates: >0 means active for some loops; <=0 means inactive for some checks; the allocator uses !=0. Thus -1 is not interchangeable with 0 across all code paths.

Conclusion
----------
The audited cleanup path and the audited d(int) loop do not restore the marker to zero. This establishes a potential slot-reuse issue if no other path clears e[1919 + slot]. It does NOT yet prove a leak: remaining bytecode write sites and whole-array reset paths must be audited before concluding that released slots can never be reused.
