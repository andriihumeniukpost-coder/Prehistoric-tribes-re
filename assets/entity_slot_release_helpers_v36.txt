Prehistoric Tribes v0.1.38 — entity-slot release helper audit (v36)

Scope
Inspected the actual javap-style disassembly of g.class in analysis/bytecode/g.txt, focusing on final void c(int), final void e(int), final void f(int), and the known release method final void a(byte).

Confirmed bytecode facts
1. final void a(byte) calls e(int), then f(int), then writes iconst_m1 / bastore to this.e[1919 + slot], then calls c(int). Therefore the marker write to -1 happens BEFORE c(slot), not after it.
2. final void c(int) does contain byte-array writes, but the inspected body writes at offsets 8810 + index and 9298 + index (and further offsets), not at 1919 + slot. It appears to process related records / references, but does not directly reset the slot marker in the visible method body.
3. final void e(int) clears values in a separate two-dimensional byte array this.a:[[B and writes zero to this.e[909 + slot]. That is a different region from the slot marker region at 1919 + slot.
4. final void f(int) updates control fields and in the inspected body does not write this.e[1919 + slot].

Interpretation
These three helpers do not provide a direct reset of the 1919-based marker in the inspected bytecode. This strengthens the unresolved concern, but does NOT prove a slot leak: other methods can write the marker through computed indices, the marker array may be reinitialized, and this audit has not performed whole-program symbolic stack tracking of every bastore.

Next decisive test
Enumerate every bastore instruction in every class method, then trace stack provenance for array references that resolve to g.e and indices equal to 1919 + slot. Also check all assignments to g.e and lifecycle / scene-reset paths. Only after that can we classify the marker transition as a genuine leak or intentional tombstone.

g.txt line 24173 onward: final void c(int), writes to 8810 + index and 9298 + index.
g.txt line 31800 onward: final void e(int), writes to this.e[909 + slot] and separate this.a:[[B.
