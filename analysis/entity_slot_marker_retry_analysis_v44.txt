2. Meaning of argument and slot-map update
-----------------------------------------
Class c, private void c(byte), bytecode 88–98 clears g.e[4444 + argument] to zero after selecting a free destination R. Before that, bytecode 113–147 copies 83 byte fields from the source slot indexed by argument (through b[S] offsets) into destination slot R (the base slot index is R, and the marker index is 1919+R). Further arrays are copied from the argument-indexed source to R at bytecode 175–233. Then counters are adjusted, and bytecode 346–356 writes zero to marker 1919+argument. Finally bytecode 357–415 registers the destination R with g.b(R) and g.g(R).

This structure strongly supports argument as the source entity/slot index being replaced: it is used as the source index for field copies, its slot-map entry at 4444+argument is cleared, and its marker is cleared only after a free destination is found and initialized. Because some indices are byte-valued and the whole game state uses packed arrays, this is strong structural evidence rather than a runtime trace.

3. Full group behavior
---------------------
In c.c(B)V:
  0–10: R = 50*u + 1
  13–26: loop while R <= 50*(u+1)
  29–45: inspect marker g.e[1919+R]; nonzero branches to 416
  416–426: R++ and loop
  429: return

If every marker in the selected group is nonzero, execution reaches 429 without performing the entity copy, clearing g.e[4444+argument], or clearing g.e[1919+argument]. No alternative branch inside this method performs those updates. Therefore this invocation does not replace the entity and does not reset the source marker.

4. Is there a retry?
-------------------
Class c.private void y() calls private boolean i() at bytecode 328 (analysis/bytecode/c.txt around line 15662). Method i() is the state-processing path that may call c.c(B)V when the state is 107. This establishes that the replacement logic is part of the entity-processing method, not an isolated constructor-only operation. It does NOT, by itself, prove how often y() is called, whether the same entity remains scheduled for later processing, or whether the state stays 107 after a failed attempt. Those points need caller/loop analysis or runtime tracing.

5. Conclusion
-------------
Confirmed:
- The argument to c.c(B)V is g.e[4444+v], not v.
- The argument is used as the source slot in the replacement/copy path.
- The old slot's mapping and marker are cleared only after a zero-marker destination slot has been found and populated.
- When all 50 markers in the selected group are nonzero, c.c(B)V returns without clearing the source slot or mapping.
- The state-107 processing method i() invokes c.c(B)V, and y() invokes i().

Not yet proven:
- That every state-107 entity is retried after a failed full-group attempt.
- That the slot-map value is always valid and in range in every execution state.
- That a global leak occurs, or that every old slot is eventually reusable.

Next: inspect y() caller scheduling and state transitions around 2828+v, plus all writes to map region 4444+index, to establish whether failed replacement remains pending and is retried when a slot later becomes free.
