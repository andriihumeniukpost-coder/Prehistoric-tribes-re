Prehistoric Tribes v0.1.38 — slot map caller audit (v50)
=====================================================

Input: v49 analysis bundle. Original game code is unchanged. This report is a static bytecode audit, not a runtime trace.

1. Caller map
-------------
The accompanying CSV records all invocation instructions found in analysis/bytecode/c.txt for the four target methods: h(int), am(), an(), and c(byte). Each row includes the enclosing method header, bytecode offset, and nearby instructions. These are direct call sites in the supplied c.txt dump; they do not establish call frequency or reachability in a particular gameplay scenario.

2. What the call sites establish
--------------------------------
- h(int) is invoked from a caller after a conditional branch, and its implementation writes k[2] to g.e[4444 + this.v]. This updates the mapping region; it is not itself a marker write.
- am() has a direct caller that performs a rendering/update call immediately before invoking it. Inside am(), mapping values are invalidated to -1 on a guarded branch; the method also writes zero to the separate region at 808 + this.v.
- an() is called from multiple branches in the supplied class dump, including branches guarded by state/range checks. Its mapping clear at 4444 + this.v is branch-dependent.
- c(byte) is called from a method when g.e[2828 + this.v] equals 107, passing g.e[4444 + this.v] as its byte argument. The callee searches the selected 50-slot group; if it finds marker zero, it copies entity data, clears the mapping for the source index, and eventually writes zero to the old marker. If it exhausts the group, it returns at bytecode offset 429 before that cleanup.

3. Marker writer scan limitation
--------------------------------
The companion CSV contains windows where a literal sipush 1919 occurs close to a bastore in the supplied bytecode dumps. It is a candidate list, not a complete proof of all marker writes: computed indices may not use a literal 1919 in the same instruction window, and aliases or helper calls can hide the write. Conversely, a nearby bastore may target another expression if control-flow and stack values are not reconstructed.

4. Current defensible conclusion
--------------------------------
A conditional cleanup path is confirmed. On the full-group branch, c(byte) returns before the successful-replacement cleanup. The call-site map confirms that c(byte) is reached from a state-107 branch in the supplied c.txt. It does not prove whether this branch is retried, whether the mapping is overwritten in a way that loses the original slot, or whether another independent path resets the marker. Therefore a permanent slot leak is still unproven.

5. Next decisive step
---------------------
Resolve the source of g.e[4444 + this.v] across every state-107 entry path, and prove whether the entity remains in state 107 and is revisited after c(byte) returns at 429. Then perform a whole-program dataflow pass for all writes to g.e[1919 + slot], including non-literal index expressions and calls through aliases.
