Animation command handler f(int, int): verified bytecode semantics
===============================================================

Method: g.f(int,int), descriptor (II)V, from analysis/bytecode/g.txt.

This is a coordinate/position update handler, not a direct sprite-index lookup. On successful branches it updates I:B and K:B, calls aK(), then sets A:Z=true. I and K appear to be the actor's two position coordinates; exact screen-axis naming is not proven by this method alone.

Argument arg1 behavior:
- arg1 > 100: indexes e[9359 + arg1 - 101] and e[9381 + arg1 - 101], subtracts C and D respectively, and adds arg2 to the second coordinate.
- 1..100: indexes e[arg1] and e[101 + arg1], applies the same coordinate-origin corrections and adds arg2 to the second coordinate.
- -100: moves I by -C and K by -(D - arg2), then completes the update.
- other negative values: uses lookup arrays e[8383 + abs(arg1)] and e[8444 + abs(arg1)], plus values from resource/blob array a indexed through h + 104 or h + 130 and an offset table e[8749 + abs(arg1)]; halves those lookup values (signed shift right), applies C/D corrections, and adds arg2 to K.
- zero and values not covered by the branches return without changing coordinates.

The final common path invokes aK() and sets A=true. This indicates that the command does more than simply increment a frame: it changes position and marks the actor/state as needing further processing.

Call-site evidence:
1. Animation step logic reads al from the animation parameter sequence. If al > 100 it calls f(al, -2); if al == 99 it calls f(p[0], -2); if al > 0 it calls f(p[al], -2); in another branch it calls f(-100, -2); and for al < 0 it calls f(al, -3). These are command dispatches, not image indices.
2. U() calls f(ak, -2) in the ag==44 branch after copying ak into ten slots of e[9601..9610].
3. Other gameplay branches call f with values from lookup tables, including f(53,-2), and call f(value,0) for movement/position adjustments.

Cautions:
- This report labels I/K as coordinate-like fields based on arithmetic with C/D and lookup tables; mapping them specifically to x/y requires confirmation from rendering code.
- e[] is a separate byte array from the resource blob a[]; offsets such as 9359, 9381, 8383, 8444, 8749 are indices into e[].
- arg2 acts as a vertical/second-coordinate adjustment in the branches shown, but its global semantic name is not established.
- The values 99 and >100 seen in al should not be interpreted as sprite IDs: the handler treats them as indices into coordinate lookup tables.
