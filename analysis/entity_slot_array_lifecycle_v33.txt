Prehistoric Tribes v0.1.38 — entity marker array lifecycle audit (v33)

Scope
-----
Static inspection of analysis/bytecode/g.txt. This report narrows the unresolved question from v32: how the byte[] field named e is initialized, and whether the disassembly shows direct reassignment of that field.

Observed evidence
-----------------
- The disassembly declares an instance field `byte[] e` (field declaration near listing line 2248).
- The listing references this field through constant-pool entry #297 as `Field e:[B` in many methods.
- A literal scan of the entire listing found zero `putfield ... // Field e:[B` instructions. Thus this listing does not show a direct assignment to the field after construction.
- The entity marker logic still indexes this array at 1919 + slot, with the allocation scan accepting only a zero byte and the release path writing -1.

Interpretation / caveat
----------------------
The absence of a direct `putfield e:[B` in this one class listing is unusual but is not enough to conclude that the field is null or that allocation is broken: the class may be initialized through inherited/obfuscated setup, the field may be populated by a different mechanism/classfile variant, or the listing could omit a relevant transformation/initializer. This audit therefore records the evidence without inferring a runtime failure.

What is still needed
--------------------
1. Confirm the exact classfile identity and constant-pool field #297 mapping against the original JAR.
2. Inspect all classes for writes to this field by owner/name/descriptor, including any inherited field with the same name.
3. Trace initialization/reset of the region [1920..1969] at runtime or through complete bytecode dataflow.
4. Only then decide whether -1 markers are normalized back to zero or whether released slots become permanently unavailable within a scene/session.

Conclusion
----------
The static evidence does not yet prove a slot leak. It does establish a useful audit target: the marker is accessed repeatedly through e:[B, while no direct assignment to that field appears in this g.class listing. Treat the field lifecycle and classfile mapping as the next verification step.
