Prehistoric Tribes v0.1.38 — marker reset path found (v42)
========================================================

Status
------
A concrete bytecode-level path that writes zero into the marker band has been identified. This resolves the earlier open question whether any reset path exists in the supplied disassemblies. It does NOT by itself prove that every release is eventually reset or that every slot is safely reusable in all circumstances.

Alias chain
-----------
1. c.<init>(g)V, analysis/bytecode/c.txt, bytecode 17–26:
   - getfield g.e:[B at offset 21
   - putfield c.a:[B at offset 24
   This establishes c.a:[B as an alias of g.e at construction.
2. In the supplied c disassembly, the only putfield to c.a:[B is this constructor assignment (constant-pool field #66). Therefore the instance field is not reassigned by any other explicit putfield in this class file.

Direct marker reset
-------------------
Method: private void c(byte); descriptor (B)V, in analysis/bytecode/c.txt.
Exact bytecode:
  346: aload_0
  347: getfield #66 // Field a:[B
  350: sipush 1919
  353: iload_1
  354: iadd
  355: iconst_0
  356: bastore

Operand-stack proof:
  arrayref = this.a, which aliases g.e
  index = 1919 + argument_1
  value = 0
Thus this is a direct store of zero to g.e[1919 + slotArgument], i.e. the marker slot band.

Reachable call sites found in supplied disassemblies
---------------------------------------------------
A. analysis/bytecode/c.txt, private boolean k()Z, invokespecial at bytecode 358:
   - checks g.e[2828 + this.v] == 107 at offsets 293–308
   - loads g.e[4444 + this.v] at offsets 344–357
   - invokes this.c(B)V at offset 358
   The value passed is a byte read from g.e[4444 + v]. This provides a concrete runtime control-flow route into the reset method when the state condition is met.

B. analysis/bytecode/g.txt, private void d(int,int) descriptor (II)V, invokespecial at bytecode 438:
   - when argument_1 equals 3 and this.aG equals 10, loads this.o:B at offsets 419–438
   - invokes this.c(B)V at offset 438
   This is a second call site into the reset method. The call-site method is on class g, so the target is g.c(B)V, not c.c(B)V; it is recorded separately and must not be conflated with the direct reset above.

Important distinction
---------------------
The direct reset proven here is c.c(B)V, because its receiver is class c and its byte-array field #66 aliases g.e. The g.d(II)V call invokes g.c(B)V, a different method with the same short name and descriptor. That call is not itself proof of the c.c(B)V reset path.

Lifecycle evidence so far
-------------------------
- Allocation in g.a(BBBBB)B requires marker 0 and writes 5..14.
- Release in g.a(B)V writes -1, then calls g.c(I)V.
- Separately, c.c(B)V contains an explicit store of 0 to the marker index.
- Therefore a reset path does exist in the supplied code, and the prior hypothesis of an unconditional permanent marker leak is not supported.
- Still unresolved: whether the reset path is reached for every released slot, how the byte argument is populated/validated, and whether the path's guards can fail or be skipped for some entity types/states. The correct conclusion is conditional reset exists; no global leak proof yet.

Suggested next analysis
-----------------------
1. Trace every caller of c.k() and determine when its return value/state handler is run.
2. Trace where g.e[4444 + v] is assigned, and whether it reliably contains the slot argument corresponding to the entity being removed.
3. Compare c.c(B)V's argument against slot ranges (1..50, 51..100, etc.) and identify how this interacts with the allocator's 50-slot groups.
4. Inspect all branches before bytecode 346 and establish whether reset can be skipped after the release path.
