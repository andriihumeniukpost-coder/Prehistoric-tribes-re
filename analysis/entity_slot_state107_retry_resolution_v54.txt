Prehistoric Tribes v0.1.38 — state-107 retry resolution (v54)
============================================================

Input: v53 bundle, including original target JAR and supplied javap-style disassemblies.
Scope: resolve the post-failure state transition as far as the current static artifacts permit. No original game code was modified.

1. Exact c.I()V branch for state 107
------------------------------------
In analysis/bytecode/c.txt, private void I(), bytecode offsets 254–345:
- offsets 254–271 load current shared state from a[2828 + v];
- offsets 272–317 handle the special state range 19..26 only when another array condition is met;
- otherwise offsets 318–344 calculate an index as aS[160] + currentState, load b[index], and pass it to c.a(int, byte) at offset 345.

For currentState = 107, the 19..26 special branch is impossible because 107 > 26. Therefore, if execution reaches this block, the requested next state is exactly b[aS[160] + 107] (with JVM byte-array indexing and signed-byte load semantics). This narrows the uncertainty to the runtime contents of aS[160] and b[] at that index.

2. Why the target byte cannot yet be responsibly stated
------------------------------------------------------
The static disassembly identifies these as instance fields supplied from g:
- c.a:[S receives g.a:[S in c.a(g), offsets 49–59;
- c.b:[B receives g.a:[B in c.a(g), offsets 39–48.
The v53 artifact set includes the original JAR and decoded tables for a different resource path (pd0), but it does not include a verified reconstruction of the live g.a:[S element 160 and g.a:[B entry at aS[160]+107. A raw resource byte or an unrelated decoded table cannot safely be substituted for these runtime values. No guessed state value is reported.

3. Consequences for retry after a full group
--------------------------------------------
The control-flow facts remain:
- c.c(B)V scans one group of 50 marker slots.
- If every marker in that group is nonzero, it returns at offset 429 before the successful-path writes to a[4444 + argument] and a[1919 + argument].
- c.k()Z continues after c.c(B)V returns.
- c.i()Z returns immediately if c.k()Z returns true; otherwise it invokes c.I()V.
- If c.I()V reaches its generic branch while the state is still 107, it requests the data-driven next state described above. The actual next state and subsequent retry behavior depend on the runtime tables and later update scheduling.

This means the failed replacement does not itself clear the old marker. But it is not enough to conclude the marker is permanently leaked: the same tick may continue through another branch, or c.I() may change state, and other lifecycle paths remain to be evaluated.

4. Current evidence status
--------------------------
Confirmed directly from bytecode:
- the state-107 dispatch passes a[4444 + v] into c.c(B)V;
- full-group failure returns before the two successful-path cleanup writes;
- c.k() continues after that call;
- c.i() invokes c.I() only when c.k() returns false;
- c.I() uses b[aS[160] + currentState] in its generic branch;
- state 107 necessarily takes that generic branch if it reaches the branch at offset 254.

Unresolved:
- runtime value of aS[160];
- runtime byte b[aS[160] + 107];
- whether the relevant c.i()/c.I() branch is reached for every failed attempt;
- whether the next state retains or discards the source-slot mapping;
- whether every possible computed-index write to marker region 1920..1969 has been excluded.

Conclusion: permanent/global slot leakage remains unproven. The next decisive step is to trace the loader that populates g.a:[S and g.a:[B from their source resource(s), reconstruct index 160 and the target byte, then continue through the resulting state handler.
