Prehistoric Tribes v0.1.38 — slot retry/control-flow audit (v51)
================================================================

Input: v50 analysis bundle. Static bytecode analysis only; no original game code changed.

1. Confirmed state-107 dispatch
-------------------------------
Class c, private boolean k(), bytecode offsets 326–361:
- 326..341 loads g.e[2828 + this.v] and compares it to 107.
- 344..358 loads g.e[4444 + this.v] and invokes private c(byte).
- 361 is the continuation after that call. Thus the caller does not return immediately merely because c(byte) was invoked.

2. Slot replacement routine
---------------------------
Class c, private void c(byte), offsets 0–429:
- 0..26 computes a candidate marker index R = 50*this.u + 1 and checks the upper bound of the current 50-slot group.
- 29..45 tests g.e[1919 + R] for zero; nonzero advances R by one and loops at 416.
- If a zero marker is found, the method copies the entity data to the selected slot.
- 88..98 clears g.e[4444 + argument] (mapping for the source index).
- 346..356 writes zero to g.e[1919 + argument], clearing the source marker.
- If all candidates are nonzero, branch to offset 429 returns without executing the successful-replacement cleanup at 88..98 and 346..356.

3. Caller continues after failed replacement
--------------------------------------------
In c.k(), the conditional call at 358 is followed by more checks, then later branches. The call to c(byte) itself does not return a success flag. The failed path in c(byte) returns normally to c.k(). This proves control returns to the caller, but does not by itself prove the state-107 value survives all subsequent processing in c.k()/c.i(); the following state handlers must be considered before asserting a retry.

4. Update scheduling evidence
-----------------------------
Class g, private void j(), offsets 0–28, calls c.g(), c.e(), c.h(), c.i() in sequence inside one exception-protected block. Class g has a caller of j() at offsets 469–490 in the method whose tail increments aQ and invokes j() when aQ > 0. This establishes a conditional update route, not a guarantee of invocation on every frame or in every scene. The constructor also contains a direct call to j() at offset 543, which is initialization-time evidence, not proof of repeated runtime construction.

5. Current defensible conclusion
--------------------------------
- A full-group failure returns before source mapping/marker cleanup.
- The state-107 handler invokes that routine using the current mapping value.
- The caller continues executing after the routine returns.
- The game has a conditional update path that invokes c.i(), which reaches the state handler.

Still unproven: whether c.i()/later state handling leaves state 107 and the source mapping intact on every failed attempt; whether subsequent updates revisit the same entity; and whether all possible marker writes elsewhere in the program have been resolved. Do not call this a proven permanent leak.

6. Next decisive checks
-----------------------
Inspect c.I() and the remaining tail of c.i() for writes to state region 2828+index or mapping region 4444+index after k() returns. Then establish the iteration/dispatch order for c.i() across entity indices and enumerate all computed-index writes to marker region 1919+slot.
